# 完成前验证

## 概述

声称工作已完成而不进行验证，这不是效率，而是欺诈。

**核心原则：** 永远先要有证据，再下断言。

**违反字面规则就是违反精神规则。**

## 铁律

```
没有新的验证证据，就不许声称完成
```

如果你在本轮对话中没有运行过验证命令，你就不能声称它通过了。

## 门禁函数

```
在声称任何状态或表达满意之前：

1. 识别：什么命令能证明这个断言？
2. 运行：执行完整命令（新鲜的、完整的）
3. 读取：完整输出，检查退出码，统计失败数
4. 验证：输出是否确认了这个断言？
   - 如果没有：用证据陈述实际状态
   - 如果有：用证据陈述断言
5. 只有这时：才能做出断言

跳过任何一步 = 撒谎，不是验证
```

## 常见失败

| 断言 | 需要 | 不充分 |
|------|------|--------|
| 测试通过 | 测试命令输出：0 失败 | 之前的运行、“应该能通过” |
| 检查器干净 | 检查器输出：0 错误 | 部分检查、推断 |
| 构建成功 | 构建命令：退出码 0 | 检查器通过、日志看起来不错 |
| Bug 已修复 | 测试原始症状：通过 | 代码改了，假设已修复 |
| 回归测试有效 | 红绿循环已验证 | 测试通过一次 |
| 代理已完成 | VCS 差异显示更改 | 代理报告“成功” |
| 需求已满足 | 逐行检查清单 | 测试通过 |

## 红旗 —— 停止

- 使用“应该”、“大概”、“似乎”
- 在验证之前表达满意（“太好了！”、“完美！”、“完成了！”等）
- 在验证之前提交/推送/PR
- 信任代理的成功报告
- 依赖部分验证
- 想“就这一次”
- 累了，想快点结束工作
- **任何没有运行验证就暗示成功的措辞**

## 合理化预防

| 借口 | 现实 |
|------|------|
| “现在应该能用了” | 运行验证 |
| “我有信心” | 信心 ≠ 证据 |
| “就这一次” | 没有例外 |
| “检查器通过了” | 检查器 ≠ 编译器 |
| “代理说成功了” | 独立验证 |
| “我累了” | 疲惫 ≠ 借口 |
| “部分检查就够了” | 部分证明不了什么 |
| “换个说法规则就不适用” | 精神高于字面 |

## 关键模式

**测试：**
```
✅ [运行测试命令] [看到：34/34 通过] “所有测试通过”
❌ “现在应该能通过了” / “看起来正确”
```

**回归测试（TDD 红绿）：**
```
✅ 编写 → 运行（通过）→ 回退修复 → 运行（必须失败）→ 恢复 → 运行（通过）
❌ “我已经写了一个回归测试”（没有红绿验证）
```

**构建：**
```
✅ [运行构建] [看到：退出码 0] “构建通过”
❌ “检查器通过了”（检查器不检查编译）
```

**需求：**
```
✅ 重新阅读计划 → 创建检查清单 → 验证每一项 → 报告缺口或完成
❌ “测试通过，阶段完成”
```

**代理委托：**
```
✅ 代理报告成功 → 检查 VCS 差异 → 验证更改 → 报告实际状态
❌ 信任代理报告
```

## 为什么这很重要

来自 24 次失败记忆：
- 你的人类搭档说“我不相信你”——信任已破裂
- 未定义函数被发布——会崩溃
- 缺失需求被发布——功能不完整
- 在虚假完成上浪费时间 → 重定向 → 返工
- 违反：“诚实是核心价值观。如果你撒谎，你就会被替换。”

## 何时应用

**在以下情况之前，永远要应用：**
- 任何成功/完成的变体声称
- 任何满意的表达
- 任何关于工作状态的积极陈述
- 提交、创建 PR、任务完成
- 转到下一个任务
- 委托给代理

**规则适用于：**
- 确切短语
- 转述和同义词
- 成功的暗示
- 任何暗示完成/正确性的沟通

## 底线

**验证没有捷径。**

运行命令。读取输出。然后再声称结果。

这是不可谈判的。
