## 阶段一：项目启动与需求澄清

### 使用 Skill：`superpowers:brainstorming`

**触发时机：**
- 用户提出"我们要做一个..."、"需要开发..."等任何创意性、构建性需求时
- 新增功能、模块、组件前
- 项目启动的第一时间

**操作步骤：**

```
Step 1: 自动触发 brainstorming skill
  ↓ 检查是否有相关 skill（系统会自动识别）
  ↓ 宣布："我正在使用 brainstorming skill 来探索项目需求"

Step 2: 探索项目上下文
  - 检查现有文件结构、文档、git 历史
  - 了解项目当前状态和技术栈

Step 3: 需求澄清（一次只问一个问题）
  - 询问项目目的、用户群体、核心痛点
  - 询问约束条件（预算、时间、技术限制）
  - 询问成功标准（如何衡量项目成功）
  - 使用选择题或开放式问题，但一次只问一个

Step 4: 提供 2-3 种方案
  - 分析不同架构/技术路线的优劣
  - 给出推荐方案并说明理由
  - 等待用户确认或调整

Step 5: 分章节呈现设计
  - 架构设计、组件拆分、数据流、错误处理、测试策略
  - 每章结束后询问用户意见

Step 6: 编写设计文档
  - 保存到：docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md
  - 确保无 TBD、TODO、矛盾、歧义
  - 提交到 git

Step 7: 用户审核设计文档
  - 请用户审核并确认是否修改
  - 用户确认后才进入下一阶段

Step 8: 触发 writing-plans skill
  - 设计确认后，自动进入实施计划阶段
```

**为什么这样操作：**
- 避免"我觉得很简单不需要设计"的陷阱，再简单的项目也有隐藏假设
- 通过一问一答模式，避免信息过载，确保理解用户真实意图
- 2-3 种方案对比，帮助用户做出明智决策，避免后期返工
- 设计文档是后续所有工作的锚点，防止实施过程中偏离目标
- 用户确认是硬门槛，杜绝"我以为用户想要这个"的幻觉

**关键原则：**
- ❌ 任何情况下，未得到设计确认前不启动代码
- ❌ 一次不问多个问题，避免用户遗漏或敷衍
- ✅ 简单项目设计可以只有几句话，但必须有
- ✅ 大型项目需要先拆解为独立子项目，逐个 brainstorm

## 阶段二：设计规划与方案制定

### 使用 Skill：`superpowers:writing-plans`

**触发时机：**
- brainstorming 阶段结束，用户已确认设计文档
- 需要为已确认的设计编写可执行的详细计划

**操作步骤：**

```
Step 1: 宣布使用 writing-plans skill
  - 宣布："我正在使用 writing-plans skill 创建实施计划"

Step 2: 评估范围
  - 检查 spec 是否覆盖多个独立子系统
  - 如果是，建议拆分为多个独立计划

Step 3: 规划文件结构
  - 明确列出所有新建/修改的文件路径
  - 每个文件只负责一个明确职责
  - 遵循项目现有代码模式

Step 4: 任务分解（任务大小适中）
  - 每个任务必须有独立的测试周期
  - 每个任务 2-5 分钟可完成一个步骤
  - 步骤示例：写失败测试 → 运行看失败 → 写最小实现 → 运行看通过 → 提交

Step 5: 编写计划文档
  - 保存到：docs/superpowers/plans/YYYY-MM-DD-<feature-name>.md
  - 必须包含：目标、架构、技术栈、全局约束
  - 每个任务包含：文件、接口（输入/输出）、具体步骤、代码示例、命令、预期输出
  - 禁止出现：TBD、TODO、"稍后实现"、"类似任务N"等占位符

Step 6: 自我审查
  - 检查 spec 覆盖度：每个 spec 要求是否对应到任务？
  - 检查占位符：全文搜索 "TBD"、"TODO"、"implement later" 等
  - 检查类型一致性：任务间函数名、签名、变量名是否一致

Step 7: 提供执行方式选择
  - 选项1：Subagent-Driven Development（推荐）- 每个任务独立子代理+审查
  - 选项2：Inline Execution - 当前会话内使用 executing-plans 执行
```

**为什么这样操作：**
- 计划是连接设计与代码的桥梁，防止"想到哪写到哪"的混乱
- 明确的文件结构规划，避免后期文件膨胀、职责混乱
- 任务粒度适中，确保每个交付物可独立测试和验证
- 无占位符原则，保证计划的完整性和可执行性
- 自我审查在计划阶段发现漏洞，比在代码阶段修复成本低 100 倍

**关键原则：**
- ❌ 计划中的每个步骤必须包含实际代码或命令，不能只是描述
- ❌ 每个任务的实现者只能看到自己的任务，接口必须精确定义
- ✅ 计划是工程师的说明书，假设他们不了解代码库和工具
- ✅ 频繁提交，每个任务结束后必须提交

## 阶段三：开发环境准备

### 使用 Skill：`superpowers:using-git-worktrees`

**触发时机：**
- 开始执行计划前
- 需要隔离的工作空间进行特性开发

**操作步骤：**

```
Step 1: 检查当前是否已隔离
  - 检测 GIT_DIR 和 GIT_COMMON 是否相同
  - 检查是否在 submodule 中（如果是，按正常 repo 处理）

Step 2: 如果已在 worktree 中
  - 报告："已在隔离工作空间 <path> 的 <branch> 分支上"
  - 跳到 Step 4

Step 3: 创建隔离工作空间
  - 询问用户是否需要隔离工作空间（如用户已有偏好，直接执行）
  - 优先使用平台原生 worktree 工具（如 EnterWorktree）
  - 如无原生工具，使用 git worktree add 回退方案
  - 目录优先级：用户指定 > 已有 .worktrees/ > 已有 worktrees/ > 默认 .worktrees/
  - 验证目录是否被 .gitignore 忽略，如未忽略则添加并提交

Step 4: 项目环境设置
  - 自动检测并安装依赖：
    - Node.js: npm install
    - Rust: cargo build
    - Python: pip install / poetry install
    - Go: go mod download

Step 5: 验证基线
  - 运行测试套件：npm test / cargo test / pytest / go test
  - 如果测试失败：报告并询问是否继续
  - 如果测试通过：报告"工作空间就绪，基线测试通过"
```

**为什么这样操作：**
- 隔离工作空间保护主分支不被污染，防止"改着改着把 main 搞坏了"
- 原生工具优先原则，避免与平台冲突产生"幻影状态"
- 基线验证确保新开发的问题是真的新问题，不是环境原有故障
- 环境准备标准化，避免"我本地可以跑"的环境差异问题

**关键原则：**
- ❌ 不在主分支（main/master）直接开发
- ❌ 不在已有 worktree 中嵌套创建另一个 worktree
- ✅ 每次创建工作空间前必须先检测是否已隔离
- ✅ 基线测试不通过必须报告，不能视而不见

## 阶段四：开发实施（核心阶段）

### 推荐 Skill：`superpowers:subagent-driven-development`

**适用场景：**
- 任务之间相对独立，可以在同一会话中连续执行
- 需要高质量输出，每步有自动审查

**备选 Skill：`superpowers:executing-plans`**

**适用场景：**
- 需要在独立会话中执行，或用户偏好批量执行
- 任务间有较强依赖，需要顺序执行

### Subagent-Driven Development 操作步骤：

```
Step 1: 预飞计划审查
  - 扫描计划，检查任务间冲突或与全局约束矛盾的地方
  - 如有问题，一次性向用户提出，不逐个打断

Step 2: 创建任务列表
  - 读取计划文件，记录上下文和全局约束
  - 创建 todo 列表跟踪所有任务

Step 3: 逐任务执行（循环）
  
  3.1 提取任务简报
      - 使用 scripts/task-brief 提取任务文本到独立文件
  
  3.2 派遣实现者子代理
      - 提供：任务位置说明、简报文件路径、前序任务接口、全局约束
      - 明确报告文件路径和输出要求
      - 模型选择：简单任务用快速模型，复杂任务用强模型
  
  3.3 处理子代理状态
      - DONE：生成审查包，进入审查
      - DONE_WITH_CONCERNS：评估担忧，决定是否继续审查
      - NEEDS_CONTEXT：补充上下文后重新派遣
      - BLOCKED：分析原因，换模型/拆分任务/升级用户
  
  3.4 任务审查（必须）
      - 生成 diff 包：scripts/review-package BASE HEAD
      - 派遣审查子代理：简报 + 报告 + diff 包 + 全局约束
      - 审查 verdict：spec 合规性 ✅/❌ + 代码质量 Approved/需修复
  
  3.5 修复循环（如审查未通过）
      - 派遣修复子代理，处理 Critical/Important 问题
      - 修复后重新审查，直到通过
      - Minor 问题记录到进度台账，不阻塞当前任务
  
  3.6 标记任务完成
      - 在 todo 列表和进度台账中记录完成状态
      - 记录 commit 范围，用于后续恢复

Step 4: 最终全分支审查
  - 生成整个分支的 diff 包：scripts/review-package MERGE_BASE HEAD
  - 派遣最终代码审查子代理（使用最强模型）
  - 处理所有发现的问题

Step 5: 完成开发
  - 使用 finishing-a-development-branch skill 处理后续流程
```

**为什么这样操作：**
- 每个任务独立子代理，上下文隔离，避免"越写越乱"
- 任务审查是质量门禁，spec 合规性防止多做/少做，代码质量防止写烂
- 修复循环确保问题在本任务内解决，不传递到后续任务
- 进度台账是故障恢复地图，即使会话崩溃也能从 git 恢复
- 模型分级使用，节省成本：机械实现用便宜模型，架构审查用最强模型

**关键原则：**
- ❌ 不并行派遣多个实现者子代理（会冲突）
- ❌ 不跳过任务审查或接受"差不多"的审查结果
- ❌ 不在审查有未解决的 Critical/Important 问题时进入下一个任务
- ✅ 每个子代理只读自己的任务简报，不读整个计划文件
- ✅ 所有产物（简报、报告、diff）通过文件传递，不粘贴到上下文

## 阶段五：测试验证与调试

### 使用 Skill：`superpowers:test-driven-development`

**触发时机：**
- 每个任务、每个功能、每个 bug 修复的编码过程中
- 是贯穿开发阶段的持续 skill，不是单独阶段

**操作步骤（RED-GREEN-REFACTOR 循环）：**

```
RED - 写失败测试
  - 一个行为一个测试
  - 测试名称清晰描述行为
  - 使用真实代码，不 mock（除非不可避）
  - 示例：test('rejects empty email', ...) 而不是 test('test1', ...)

Verify RED - 运行看失败
  - 运行测试命令（如：npm test path/to/test.test.ts）
  - 确认：测试失败（不是报错）
  - 确认：失败信息是预期的（如："function not defined"）
  - 如果测试通过→说明测的是已有行为，修改测试
  - 如果测试报错→修复错误直到能正确失败

GREEN - 最小实现
  - 写最简单的代码让测试通过
  - 不添加额外功能、不重构、不"优化"
  - 示例：if (!email) return { error: 'Email required' } 而不是引入验证库

Verify GREEN - 运行看通过
  - 运行测试，确认通过
  - 确认其他测试仍然通过
  - 确认输出干净（无错误、无警告）
  - 如果失败→修复代码，不修改测试（除非测试写错）

REFACTOR - 清理
  - 只在测试通过后重构
  - 消除重复、改善命名、提取辅助函数
  - 保持测试通过，不添加行为

Repeat - 下一个测试
```

### 使用 Skill：`superpowers:systematic-debugging`

**触发时机：**
- 测试失败、生产 bug、意外行为、性能问题、构建失败
- 尤其是：时间紧迫时、"显而易见的修复"时、已尝试多次修复未果时

**操作步骤（四阶段法）：**

```
Phase 1: 根因调查（任何修复前必须完成）
  1. 仔细阅读错误信息（不跳过堆栈、行号、错误码）
  2. 稳定复现问题（记录精确步骤、确认是否每次都发生）
  3. 检查近期变更（git diff、最近提交、新依赖、环境变化）
  4. 多组件系统：添加诊断日志，追踪每层边界的数据流入/流出
  5. 数据流追踪：从错误点向上追溯，找到坏数据的源头
  → 成功标准：理解 WHAT 和 WHY

Phase 2: 模式分析
  1. 在代码库中找到类似但工作正常的代码
  2. 与参考实现完整对比（逐行阅读，不跳读）
  3. 列出所有差异，无论多小（不假设"这个不重要"）
  4. 理解依赖关系（组件、配置、环境、假设）

Phase 3: 假设与验证
  1. 提出单一明确假设："我认为 X 是根因，因为 Y"
  2. 做最小改动验证假设（只改一个变量）
  3. 验证结果：
     - 有效 → 进入 Phase 4
     - 无效 → 提出新假设，不叠加修复
  4. 不知道时：诚实说"我不理解 X"，寻求帮助

Phase 4: 实现修复
  1. 创建失败测试（最简单的复现，使用 test-driven-development skill）
  2. 实施单一修复（针对根因，不是症状）
  3. 验证：测试通过？无其他测试破坏？问题真正解决？
  4. 如果失败：
     - 尝试 < 3 次：返回 Phase 1，用新信息重新分析
     - 尝试 >= 3 次：STOP，质疑架构是否有根本问题，与用户讨论
```

**为什么这样操作：**
- TDD 的"先写测试"确保你测试的是"应该发生什么"而不是"代码做了什么"
- 看测试失败是验证测试有效性的唯一方式，跳过的测试可能是"假测试"
- 系统调试的"四阶段法"防止"试试这个、试试那个"的随机修复，减少引入新 bug
- 3 次修复失败即质疑架构，防止在错误的设计上不断打补丁
- 根因修复 vs 症状修复：修根因一次解决，修症状反复出现

**关键原则：**
- ❌ 严禁"先写代码再补测试"——如果已经写了，删除重写
- ❌ 严禁"测试通过后我觉得还需要优化一下"在 GREEN 阶段添加功能
- ❌ 严禁"先 quick fix 一下再调查"
- ✅ 每个新函数/方法必须有测试，且必须看过它失败
- ✅ 测试名称中出现"and"→ 拆分成两个测试

## 阶段六：代码审查与质量把控

### 使用 Skill：`superpowers:requesting-code-review`

**触发时机：**
- Subagent-Driven Development 的每个任务完成后（强制）
- 完成主要功能后（强制）
- 合并到 main 前（强制）
- 卡壳时、重构前、修复复杂 bug 后（可选但推荐）

**操作步骤：**

```
Step 1: 获取 git 提交范围
  BASE_SHA=$(git rev-parse HEAD~1)  # 或 origin/main
  HEAD_SHA=$(git rev-parse HEAD)

Step 2: 派遣代码审查子代理
  - 使用 general-purpose 子代理
  - 填充模板：
    - DESCRIPTION：简要说明做了什么
    - PLAN_OR_REQUIREMENTS：应该做什么（计划或需求）
    - BASE_SHA：起始提交
    - HEAD_SHA：结束提交
  - 审查子代理不继承当前会话历史，只审查工作产物

Step 3: 处理审查反馈
  - Critical 问题：立即修复
  - Important 问题：修复后再继续
  - Minor 问题：记录，稍后处理
  - 如果审查者错误：用技术推理反驳，展示代码/测试证明
```

### 使用 Skill：`superpowers:receiving-code-review`

**触发时机：**
- 收到代码审查反馈时（无论是人还是代理审查）
- 实施审查建议前，尤其是反馈看起来不清楚或技术上有疑问时

**操作步骤：**

```
Step 1: 完整阅读（不立即反应）
  - 读完所有反馈再动手

Step 2: 理解（用自己的话复述）
  - 对每条反馈："这条要求我修改 X，因为 Y"
  - 不懂就问："我需要澄清第 4 和第 5 条"

Step 3: 验证（对照代码库现实）
  - 这条建议在当前代码库中技术上正确吗？
  - 会破坏现有功能吗？
  - 审查者了解完整上下文吗？
  - 与用户之前的决策冲突吗？

Step 4: 评估（技术合理性）
  - 如果建议错误：用技术推理反驳，引用测试/代码
  - 如果建议涉及未使用功能（YAGNI）：grep 代码确认，提议删除而非实现
  - 如果无法验证：诚实说明，询问应该调查/询问/继续

Step 5: 回应（技术确认，不表演式感谢）
  - ✅ "Fixed. 将 magic number 提取为常量 PROGRESS_INTERVAL。"
  - ✅ "Good catch - 这里确实有竞态条件。已在 [文件] 修复。"
  - ❌ "You're absolutely right!"
  - ❌ "Great point!"

Step 6: 实施（按顺序）
  - 先澄清所有不清楚的项
  - 按顺序：阻塞性问题 > 简单修复 > 复杂重构
  - 每项单独测试，确认无回归
```

**为什么这样操作：**
- 代码审查是防止问题级联的闸门，在本任务发现比在下个任务发现便宜 10 倍
- 审查者独立视角，不受开发者思维定势影响，能发现盲点
- 技术严谨性优先于社交舒适，"谢谢"不能替代正确的代码
- 验证审查建议可防止"审查者不了解上下文"导致的错误修改
- YAGNI 检查防止实现没人用的功能，避免代码膨胀

**关键原则：**
- ❌ 不因为"很简单"跳过审查
- ❌ 不忽略 Critical 问题
- ❌ 不用"感谢""你说得对"等表演式回应，用技术描述替代
- ✅ 不懂就问，不要部分理解就实施
- ✅ 外部反馈是建议需要评估，不是命令必须执行

## 阶段七：项目完成与上线交付

### 使用 Skill：`superpowers:verification-before-completion`

**触发时机：**
- 任何声称"完成"、"修复了"、"通过了"之前
- 提交、创建 PR、标记任务完成、委派给代理之前
- 每次完成一个开发单元时

**操作步骤：**

```
Step 1: 识别验证命令
  - "我声称测试通过" → 验证命令是 npm test / cargo test / pytest
  - "我声称构建成功" → 验证命令是 npm run build / cargo build
  - "我声称 bug 修复" → 验证命令是复现测试的 red-green 循环

Step 2: 运行完整命令（不是部分，不是"应该可以"）
  - 在这个消息中执行完整命令
  - 不依赖之前的运行结果

Step 3: 阅读完整输出
  - 检查退出码
  - 统计失败数
  - 检查是否有警告、错误

Step 4: 验证输出是否支持声称
  - 如果否：陈述实际状态，附证据
  - 如果是：陈述声称，附证据

Step 5: 只有此时，才做出声称
  - ✅ "[运行测试] [看到 34/34 通过] 所有测试通过"
  - ❌ "应该可以了" / "看起来正确" / "完成了！"
```

### 使用 Skill：`superpowers:finishing-a-development-branch`

**触发时机：**
- 实现完成，所有测试通过，需要决定如何集成代码

**操作步骤：**

```
Step 1: 验证测试（必须先做）
  - 运行项目测试套件
  - 如果失败：报告失败，停止，不进入下一步
  - 如果通过：继续

Step 2: 检测环境
  - 检测当前是正常 repo、命名分支 worktree、还是 detached HEAD
  - 确定合并目标分支（main/master）

Step 3: 呈现选项（精确这 4 个）
  正常 repo 和命名分支：
  1. 本地合并回 <base-branch>
  2. 推送并创建 Pull Request
  3. 保持分支现状（稍后处理）
  4. 丢弃此工作
  
  Detached HEAD：
  1. 推送为新分支并创建 PR
  2. 保持现状
  3. 丢弃

Step 4: 执行用户选择
  
  选项 1 - 本地合并：
    - 切换到 main，拉取最新
    - 合并特性分支
    - 验证合并后的测试
    - 清理 worktree（如果是 superpowers 创建的）
    - 删除特性分支
  
  选项 2 - 创建 PR：
    - 推送分支到 origin
    - 不清理 worktree（用户需要它来迭代 PR 反馈）
  
  选项 3 - 保持现状：
    - 报告："分支 <name> 已保留，worktree 在 <path>"
  
  选项 4 - 丢弃：
    - 要求用户输入 "discard" 确认
    - 列出将被删除的分支、提交、worktree
    - 确认后：清理 worktree，删除分支
```

**为什么这样操作：**
- verification-before-completion 是诚实门槛，防止"我觉得可以了"导致的未验证代码上线
- 证据先于声称，确保每次"完成"都是真实的、可复现的
- finishing-a-development-branch 提供结构化选项，避免"然后呢？"的迷茫
- 测试验证是合并的硬门槛，防止把问题带入主分支
- 清理 worktree 的严谨顺序（先合并再删 worktree 再删分支）避免 git 错误

**关键原则：**
- ❌ 不在验证前声称完成（包括"Great!""Done!""完美！"等情绪表达）
- ❌ 不基于"之前的运行""应该可以""我有信心"做出判断
- ❌ 不删除不是自己创建的 worktree
- ✅ 选项 4 丢弃必须输入 "discard" 确认，防止误删
- ✅ 只有选项 1 和 4 清理 worktree，选项 2 和 3 保留

## 常见误区与避坑指南

### 误区一："需求很简单，不需要 brainstorm"
**风险：** 未探索的假设导致方向偏差，后期返工成本高。
**正确做法：** 无论多简单，都使用 brainstorming。简单项目的设计可以只有几句话，但必须有。

### 误区二："计划里有 TODO 没关系，以后补"
**风险：** 计划不完整导致执行时遗漏，工程师无所适从。
**正确做法：** writing-plans 的"无占位符"规则是硬性的。任何 TBD/TODO 都必须在计划阶段解决。

### 误区三："这次改动小，直接改 main 就行"
**风险：** 污染主分支，影响其他开发者，回滚困难。
**正确做法：** 无论改动大小，使用 using-git-worktrees 创建隔离空间。

### 误区四："先写代码，测试稍后补"
**风险：** 测试可能测的是已实现行为而非需求行为，测试质量低，且无法验证测试是否有效。
**正确做法：** 严格执行 test-driven-development。如果已经先写了代码，删除它，重新开始。

### 误区五："这个 bug 很明显，直接改就行"
**风险：** 症状修复掩盖根因，可能引入新 bug，同一问题反复出现。
**正确做法：** 使用 systematic-debugging，完成四阶段调查后再修复。如果 3 次修复失败，质疑架构。

### 误区六："审查就是走个形式，肯定没问题"
**风险：** 问题在任务间级联，到后期修复成本指数级增长。
**正确做法：** 每个任务后都使用 requesting-code-review。审查是质量门禁，不是形式主义。

### 误区七："测试应该通过了，我就不运行了"
**风险：** 未验证的代码可能包含未发现的错误，破坏信任。
**正确做法：** 使用 verification-before-completion。任何完成声称前，必须有运行的命令和输出作为证据。

## 总结

Superpowers 的 skill 体系是一个**防御性编程方法论**在 AI 辅助开发中的体现。每个 skill 都是一道质量闸门：

| 阶段 | Skill | 防御目标 |
|------|-------|----------|
| 需求 | brainstorming | 防止理解偏差 |
| 计划 | writing-plans | 防止实施混乱 |
| 环境 | using-git-worktrees | 防止环境污染 |
| 开发 | subagent-driven-development + TDD | 防止质量滑坡 |
| 调试 | systematic-debugging | 防止随机修复 |
| 审查 | requesting/receiving-code-review | 防止问题级联 |
| 完成 | verification-before-completion | 防止虚假完成 |
| 集成 | finishing-a-development-branch | 防止集成错误 |

**核心信条：** 不跳过一个 skill，不跳过一步验证。证据先于声称，测试先于代码，审查先于合并。这样，你的 Web 项目从需求到上线，每一步都有据可查、有质可保。 🎯
